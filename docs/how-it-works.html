The robot that signs up to sites and grabs the API key

Plain-language walkthrough · each box = one thing it does, top to bottom · mirrors farmer/tree.py → run_site()

What it does, in one line: opens the site, signs in with your Google (or GitHub) account, skips the useless screens, goes to where the API key lives, copies it. If a site has a wall it can't pass (asks for a phone number, wants a credit card, blocks bots), it skips it and records why instead of hammering a dead end.
Single source of truth: every fact about a site — URL, where the key page is, the key's shape, known walls — lives in one place: data/sites.json. The code always reads from there, so nothing drifts out of sync.
main step deterministic (no AI) check / action decision (yes/no) site registry AI fallback stops / skips
THE SITE REGISTRY — the instruction sheet
One row per site in data/sites.json + data/sites_extra.json. It says: the site's URL · where the key page is (key_url) · the key's shape (key_re, so it can recognise it) · is there a known wall? (automatable / wall). The code always reads from here — one source, no conflicting copies.
START · takes the sites one at a time
If you dropped an out/STOP file, it stops before the next site (never mid-site). If a site already produced a key for this account on an earlier run, it skips it — never redoes a site+account pair already in out/keys.txt.
DECISION · does the registry mark this site as un-automatable?
Read straight from sites.json (registry.automatable()). If yes → skip immediately and record the wall (e.g. "blocks bots"). It never bangs against a known wall — even if you asked for that site by name, it tells you "there's a wall" instead of trying in vain.
YES — known wall (e.g. HuggingFace)
skip, record why, move to next site
status: "wall" with the reason. HuggingFace silently blocks bots; the only ways left are a password-reset via email in a clean session, or a real password you supply.
NO — automatable → continue
the real flow for that site begins ↓
OPEN the site
The Chrome profile is already signed into your Google account → it often lands logged-in with no work. (Multi-account: an optional sign-out first forces Google's account chooser.)
1DISMISS the cookie banner
cookies.dismiss() — clicks "Reject" using known CMP selectors, with a semantic text fallback (reject/decline/necessary only). Careful not to mis-click a trap (an early bug clicked "Bookmark"; fixed).
NEW · early "Continue with GitHub" branch
For sites that sign in via GitHub (declared via_github) it tries the GitHub button right away — waits for the SPA to render it, and if it's not on the landing page, navigates to the auth page (via Log in) and retries. If it lands, skip signup and go straight to the key page.
DECISION · am I already on the key page?
_is_key_area(): if the URL mentions keys/dashboard and the body talks about "API key / create key" (positive signals win, even if the header still shows "Log in" — that false-negative used to loop on Nebius) → already in → skip all of signup, jump to step 6.
2FIND the signup entry
links.find_and_click("signup"); if there's no "Sign up", try "Sign in" (on many sites signing in with Google = registering). Nothing found → ask the AI. Avoids trap links (blog, docs, pricing, social).
3SIGN IN (three routes)
Route A — Google button (preferred)
"Continue with Google" → pick your account → "Allow"
google_oauth.signup_with_google() then a settle loop: while still on a Google host, handle_google_page() types the email, the password (from ~/.google_pw), and clicks the consent.
Route B — GitHub button
github_oauth.signup_with_github() → tick Terms → Authorize
Tried when Google didn't take and a GitHub button exists.
Route C — email/password form (no OAuth)
DECISION · does it ask for a phone number?
Hard rule: yes → drop the site (forms.has_phone() → no_key). Phone can't be automated. Re-checked again after submitting the form.
forms.fill_form() + submit
Fills email/password/name into the right fields only. If it stalls → hands to the AI.
4EMAIL verification (only if the site asks)
If you signed in with Google it's already verified → skipped. Otherwise, if the page says "check your email", the AI tries to click the confirmation link.
5SKIP the welcome screens
Up to 4 rounds of clicking "Skip / Maybe later / Not now / No thanks" on useless intro prompts. None there → move on.
6GET the key
Navigate to the key page (key_url from the registry) and dismiss any cookie banner there too.

grabkey.grab_key() — how it reads the key, in order:
1) is it already shown in plain text? (recognised by key_re) → taken, done.
2) is it masked with dots? → click "Copy" and read it from the clipboard.
3) not there? → click "Create key", name it (_fill_key_name), pick required dropdowns (_select_required), confirm, wait for it to appear, read it.
Each site has a quirk (on Groq the confirm button says "Submit" and sits outside the panel; on Mistral it's inside) — handled in the code.
NEW · if no key yet → forms.complete_form() (generic, deterministic)
Many "walls" are just an onboarding form: it fills email/password/name/organization, ticks the consent checkboxes (scroll-into-view + force, works even on hidden custom checkboxes), and submits (skips a disabled button until consents are ticked). One reusable component, no per-site recipes.
NEW · learned.py — replay what the AI already solved
Every action the AI resolves successfully is saved as a deterministic recipe (page path + element type + action). On later runs those recipes are replayed before calling the AI — zero AI cost, and the system gets more reliable the more sites it touches.
still stuck → ai_fallback.ai_step() (time-boxed, loop-detected, vision as last resort) → then re-read the key

MULTI-ACCOUNT — grab the key with a second/third account
Set SIGNUP_PROFILE to a separate Chrome sub-profile already signed into another Google account, and SIGNUP_ACCOUNT to match — Google then auto-picks that account, no chooser, no stored passwords. It never redoes a site+account pair already saved.

THE PATTERN: where the code wins and where it can't
WINS when a site has "Continue with Google" (or GitHub) and shows the account chooser. Can't pass when the wall is external, not a code bug: a phone number, a credit card, a scoped-token-only flow (Cloudflare), a re-asked password (AI21), a down server (Glhf), or a silent bot block (HuggingFace). These are recorded with their reason rather than retried in vain. The remaining hard case is a few React-controlled custom onboarding forms where a hidden checkbox resists automation.
The deterministic path (steps 1–6) handles most sites end-to-end; forms.complete_form and the learned.py replay reduce how often the AI is needed. Free-tier keys are obtained for 9 providers (×3 accounts = your vault). The failing providers all hit an external wall, not a code error.
